# talent-api 토큰 발급 · 보관 · 로테이션 절차 (초안)

**상태:** 초안 (draft) — COU-2103 산출물. 배포 선행 조건 3.
**근거:** COU-2079 결정 2(a) · 백엔드 인증 게이트 COU-2064 · 프런트 프록시 COU-2103
**적용 대상:** `talent-db-frontend` (Vercel) ↔ `talent-api`

> 이 문서에는 **실제 토큰 값이나 예시 토큰 문자열이 하나도 없다.** 형식만 설명한다.
> 값을 이 문서, PR 본문, 이슈 코멘트, 스크린샷에 붙여넣는 것은 금지다.

---

## 0. 한 줄 요약

bearer 토큰은 **서버 env 전용**이다. 브라우저는 토큰을 절대 보지 않고
`/api/proxy/*` · `/api/media/*` 서버 라우트만 호출한다. `NEXT_PUBLIC_*` 접두사로
토큰을 노출하는 것은 **결정으로 금지**되어 있다.

---

## 1. 왜 `NEXT_PUBLIC_*` 가 금지인가

Next.js 는 `NEXT_PUBLIC_` 으로 시작하는 env 를 **빌드 시점에 클라이언트 번들에 문자열로
인라인**한다. 즉 브라우저 개발자도구에서 누구나 읽을 수 있고, 배포 산출물에 영구히
박힌다. 그런 값은 비밀이 아니다.

COU-2078 에서 이 트레이드오프가 제기되어 COU-2079 결정 2(a) 로 다음이 확정되었다.

- bearer 토큰은 **서버 env 전용** (`TALENT_API_TOKEN`)
- 브라우저는 **NextJS 서버 라우트 프록시만** 호출
- `NEXT_PUBLIC_*` 토큰 사용은 **명문 금지**

검증 방법은 §7 참고.

---

## 2. env 이름과 역할

| env 이름 | 위치 | 역할 |
|---|---|---|
| `TALENT_API_BASE_URL` | 서버 전용 | talent-api 업스트림 오리진. 프록시가 이 값으로 호스트를 **고정**한다(SSRF 방지의 축). |
| `TALENT_API_TOKEN` | 서버 전용 | talent-api bearer 토큰. 서버 라우트 핸들러에서만 읽힌다. |

- 두 값 모두 `NEXT_PUBLIC_` 접두사를 붙이면 안 된다.
- 코드상 유일한 접근 지점: `lib/server/talent-api.ts` (클라이언트 import 시 즉시 throw).
- `.env.example` 에는 **이름만** 있고 값은 빈칸이다. `.env*` 는 `.gitignore` 대상.

### 토큰 형식

- 사람이 만든 문자열이 아니라 **CSPRNG 로 생성한 고엔트로피 랜덤 문자열**을 쓴다.
  권장: 32바이트 랜덤 → URL-safe base64 또는 hex 인코딩.
- 생성 예시 명령(값은 기록하지 말 것): `openssl rand -base64 32`
- 사람이 읽는 접두사(환경 구분용)는 붙여도 되지만 그 자체가 비밀성을 대신하지 않는다.
- 토큰에 의미(사용자 식별, 권한 정보)를 인코딩하지 않는다. 단순 불투명 값이다.

## 3. 발급 주체와 경로

| 단계 | 담당 | 내용 |
|---|---|---|
| 1 | Backend (talent-api 소유자) | CSPRNG 로 새 토큰 생성 |
| 2 | Backend | 백엔드 `API_AUTH_TOKENS`(COU-2064) 에 **추가** (기존 토큰 제거하지 않음) |
| 3 | Backend → Frontend 배포 담당 | 값을 **1:1 비공개 시크릿 채널**로 전달 |
| 4 | Frontend 배포 담당 | Vercel Encrypted Environment Variable 로 `TALENT_API_TOKEN` 설정 |
| 5 | Frontend 배포 담당 | 재배포 후 §7 검증 수행 |
| 6 | Backend | 구 토큰 폐기 (§5) |

**전달 시 금지 경로:** 이슈 코멘트, PR 본문, 커밋 메시지, 공용 채팅 채널, 스크린샷,
문서, 로그, 티켓 첨부파일. 값은 항상 시크릿 관리 도구 또는 1:1 비공개 채널로만.

**최소 권한:** 프런트엔드용 토큰은 프런트엔드 전용으로 발급한다. 다른 클라이언트
(배치 잡, 관리 스크립트 등)와 **같은 토큰을 공유하지 않는다** — 공유하면 한쪽만
로테이션할 수 없다.

## 4. 보관 위치

### 허용

- **Vercel Encrypted Environment Variables** — 환경별로 분리 (Production / Preview / Development).
  Preview 와 Production 은 **서로 다른 토큰**을 쓴다.
- 로컬 개발: `.env.local` (`.gitignore` 대상, 커밋 금지)
- 전달 중 임시 보관: 조직 승인된 시크릿 관리 도구

### 금지

- `NEXT_PUBLIC_*` env (§1)
- 저장소에 커밋되는 모든 파일 (`.env.example` 포함 — 이름만)
- 클라이언트 컴포넌트, 클라이언트 번들에 포함되는 모듈
- 이슈/PR/커밋/문서/스크린샷/공용 채널
- 애플리케이션 로그. 프록시 라우트는 예외 메시지·URL·헤더를 로그와 응답 본문에
  담지 않는다 (`lib/server/talent-api.ts` 의 `proxyError()` 는 고정 문구만 반환).

---

## 5. 백엔드 `API_AUTH_TOKENS` 와의 대응 관계

- 백엔드는 **여러 개의 유효 토큰을 동시에 허용**한다 (COU-2064, `API_AUTH_TOKENS`).
  이것이 무중단 로테이션의 전제다.
- 프런트엔드는 그중 **정확히 하나**를 `TALENT_API_TOKEN` 으로 들고 있다.
- 관계: `TALENT_API_TOKEN` ∈ `API_AUTH_TOKENS`
- 따라서 **추가는 백엔드 먼저, 제거는 프런트엔드 교체 후**가 항상 옳은 순서다.
  이 순서를 뒤집으면 프런트엔드가 전면 401 이 된다.

## 6. 로테이션

### 주기

| 상황 | 주기 |
|---|---|
| 정기 | **90일** |
| 담당자 이탈 · 권한 변경 | 즉시 |
| 유출 의심 | 즉시 (§8) |
| 신규 환경 추가 | 환경별 신규 발급 |

### 무중단 절차 (overlap rotation)

두 토큰이 동시에 유효한 구간을 만들어 다운타임 없이 교체한다.

1. **생성** — Backend 가 새 토큰 `T_new` 생성 (§2 형식).
2. **추가** — `API_AUTH_TOKENS` 에 `T_new` 를 **추가**. `T_old` 는 그대로 둔다.
   백엔드 배포 후 두 토큰 모두 유효한지 확인.
3. **전달** — `T_new` 를 비공개 채널로 Frontend 배포 담당에게 전달.
4. **교체** — Vercel `TALENT_API_TOKEN` 을 `T_new` 로 갱신 → **재배포**.
   (Vercel env 변경은 재배포 없이는 런타임에 반영되지 않는다.)
5. **검증** — §7 체크리스트. 401 배너가 뜨지 않고 데이터·미디어가 모두 로드되는지 확인.
6. **폐기** — 최소 **24시간** 관찰 후 `API_AUTH_TOKENS` 에서 `T_old` 제거, 백엔드 재배포.
   (관찰 구간은 롤백 여지를 남기기 위한 것이다.)
7. **기록** — §9 감사 로그에 기재.

Preview / Production 환경은 각각 위 절차를 독립적으로 수행한다.

### 롤백

6단계 이전이라면 `T_old` 가 아직 유효하므로 Vercel env 를 `T_old` 로 되돌리고
재배포하면 즉시 복구된다. 6단계 이후에는 `T_new` 로만 복구 가능하다.

## 7. 배포 전·후 검증 체크리스트

1. `npx tsc --noEmit` · `npm run lint` · `npm run build` 통과
2. **클라이언트 번들에 토큰 없음** — 빌드 후 아래 grep 결과가 모두 0건이어야 한다.
   검색어와 건수만 기록하고 값은 기록하지 않는다.
   ```
   grep -rlI 'TALENT_API_TOKEN'   .next/static   # 0건
   grep -rlI 'NEXT_PUBLIC_API_TOKEN' .next/static # 0건
   grep -rlI '<토큰 값>'           .next          # 0건
   ```
   재현 가능한 방식: 가짜 sentinel 값으로 빌드해 `.next` 전체에서 sentinel 이
   0건인지 확인한다 (실토큰으로 검증할 필요 없음).
3. `grep -rn 'NEXT_PUBLIC' app components lib` 결과에 토큰 관련 항목이 없어야 한다.
4. 프록시 동작 — 정상 경로 200, 화이트리스트 밖 404, 경로 이스케이프 400,
   `DELETE`/`PUT` 405, 업스트림 401 은 401 그대로 전달.
5. 미디어 — `/api/media/*` 가 200/206 으로 오고 `Cache-Control: private, no-store`,
   `X-Robots-Tag: noindex, nofollow` 가 붙는지 확인.
6. 브라우저 네트워크 탭에 업스트림 호스트로 직접 나가는 요청이 **0건**인지 확인.

## 8. 유출 시 즉시 폐기 절차

유출이 **의심**되는 순간 확인을 기다리지 않고 시작한다.

1. **차단(T+0)** — Backend 가 `API_AUTH_TOKENS` 에서 해당 토큰을 **즉시 제거**하고
   배포한다. 프런트엔드가 401 이 되는 것을 감수한다 (401 배너가 사용자에게 상태를
   알리고 무한 재시도는 일어나지 않는다 — COU-2078).
2. **신규 발급(T+0)** — §6 절차로 새 토큰을 발급해 프런트엔드를 복구한다.
   (차단과 병렬로 진행하여 다운타임을 줄인다.)
3. **범위 파악** — 유출 경로(스크린샷·로그·커밋·채널)를 특정하고, 같은 토큰을 쓰는
   다른 클라이언트가 있는지 확인한다.
4. **흔적 제거** — 커밋 히스토리·로그·문서에서 값을 제거한다. 단, **이미 유출된
   토큰은 제거로 무효화되지 않는다** — 폐기(1단계)가 유일한 무효화 수단이다.
5. **접근 검토** — talent-api 접근 로그에서 해당 토큰의 비정상 사용(미승인 IP,
   비정상 시간대, 대량 조회)을 확인한다. 미성년 PII 접근이 포함되면 상위 이슈
   (COU-2056 계열)로 즉시 에스컬레이션한다.
6. **기록** — §9 감사 로그에 사건으로 기재.

## 9. 감사 로그

토큰 관련 모든 사건을 기록한다. **값은 절대 기록하지 않는다.**

기록 위치: 이 문서 아래 표 (또는 조직 표준 보안 로그).

| 일시 (UTC) | 사건 | 환경 | 토큰 식별자(값 아님) | 수행자 | 승인자 | 비고 |
|---|---|---|---|---|---|---|
| | | | | | | |

- **토큰 식별자**는 값이 아니라 `2026-07-frontend-prod-1` 같은 라벨이나 값의
  SHA-256 앞 8자리 등 **역산이 불가능한 식별자**를 쓴다.
- 기록 대상 사건: 발급, 환경 설정/변경, 로테이션 각 단계, 폐기, 유출 대응.
- talent-api 측 접근 로그(요청 주체·경로·상태코드)는 백엔드 책임이며, 로그에
  토큰 값이나 Authorization 헤더 원문이 남지 않아야 한다.

## 10. 미해결 항목 (배포 전 결정 필요)

1. **프록시 라우트 자체의 인증** — `/api/proxy/*` 와 `/api/media/*` 는 같은 오리진
   요청이면 누구나 호출할 수 있다. 앱의 `/login` 은 클라이언트 사이드 쿠키 설정일
   뿐이라 **보안 경계가 아니다.** 즉 이 프록시는 talent-api 토큰을 숨기지만
   **앱 자체를 인증하지는 않는다.** 현재 유일한 실질 차단은 Vercel Deployment
   Protection 이며, 이것이 켜져 있는 동안에만 안전하다.
   → 서버측 세션 도입은 별도 이슈로 다뤄야 한다. **Deployment Protection 을 끄기 전에
   반드시 선행되어야 한다.**
2. **업스트림 리다이렉트** — 프록시는 `redirect: 'manual'` 이고 3xx 는 502 로 막는다.
   talent-api 가 미디어를 CDN 으로 302 하게 되면 별도 대응이 필요하다.
3. **감사 로그 보관 위치** — 이 문서 표 / 조직 보안 로그 중 어디를 정본으로 할지 미정.
